# SIMSIM — تقرير تثبيت رحلة التسجيل وتهيئة المالك

**تاريخ التقرير:** 19 أغسطس 2026  
**النطاق:** رحلة التسجيل من إنشاء الحساب، مرورًا بتأكيد البريد والجلسة وإنشاء المطعم، وحتى Onboarding وإنشاء المنيو.  
**حالة تغييرات الكود:** جاهزة للمراجعة المحلية؛ لم تُدمج أو تُنشر من هذه المرحلة بعد.

> **حكم التحقق الحالي:** الإصلاحات اجتازت اختبارات المشروع والبناء وفحصًا بصريًا محليًا للمسارات العامة. أمّا التحقق E2E الحقيقي من إنشاء حساب مؤكد، واستلام رابط البريد، وإكمال Onboarding بمالك مصرح به، فهو **NOT VERIFIED — REAL OWNER SESSION REQUIRED**. لا يُعامل ذلك على أنه PASS أو دليل إنتاجي.

## ROOT CAUSE

كانت الرحلة تحتوي على أكثر من نقطة تقرر حالة الجلسة والوجهة بصورة مستقلة. في التهيئة السابقة، ينتهي `loading` قبل أن تكتمل بالضرورة قراءة سياق المطعم، بينما تُعالج أحداث Supabase مثل `INITIAL_SESSION` و`SIGNED_IN` في مسار منفصل. وقد يسمح ذلك بحالة انتقالية يكون فيها `user` موجودًا بينما `restaurant` لم يُحمّل بعد، وهي حالة كافية لعرض fallback غير صحيح أو توليد انتقال متنافس في المسارات المحمية. تم أيضًا تنفيذ الاستئناف وتقرير الوجهة سابقًا من أكثر من صفحة، ما يضاعف احتمال سباق الطلبات بعد callback أو تسجيل الدخول. [1]

في Onboarding، كان الاعتماد الرئيس على حالة React `saving` لمنع النقر المزدوج. لا تصبح هذه الحالة نافذة فورًا بين نقرات متقاربة، ولم توجد حالة خطأ مرئية قابلة لإعادة المحاولة عند فشل تحميل المطعم. كذلك لم تكن هناك قراءة وقائية لوجود أقسام في الفرع الأساسي قبل إدراج قالب المنيو؛ لذلك كان خطر التكرار قائمًا في إعادة المحاولة أو التدفق المتسارع ضمن الجلسة نفسها. [2]

| السبب | الأثر المحتمل قبل الإصلاح | المعالجة المنفذة |
|---|---|---|
| إنهاء التحميل قبل اكتمال سياق المالك | انتقال مبكر أو شاشة حالة غير صحيحة | bootstrap واحد يبقي `loading` فعالًا حتى الجلسة والمطعم والقدرات وتقرير الوجهة |
| استئناف المطعم والـredirect من مسارات متعددة | طلبات مكررة وقرارات وجهة متعارضة | `completeAuthSession()` و`resolveUserDestination()` كمصدرين مركزيين للحقيقة |
| استجابة Auth متأخرة بعد تبدّل الحساب أو تسجيل الخروج | كتابة بيانات جلسة قديمة في المتجر | عدادات إصدار وإبطال للطلبات المتأخرة قبل أي تحديث للحالة |
| الاعتماد على `saving` فقط | إنشاء مطعم أو منيو مكرر بالنقر السريع | أقفال `useRef` متزامنة، إضافة إلى فحص البيانات الحالية |
| فشل تحميل Onboarding بلا واجهة تعافٍ | احتمال صفحة فارغة أو تجربة عالقة | مرحلة خطأ واضحة مع زر إعادة المحاولة والعودة لتسجيل الدخول |

## FIX

يبدأ التطبيق الآن بتسجيل مستمع Supabase مرة واحدة قبل طلب الجلسة. عند وجود جلسة، يمر كل من `INITIAL_SESSION` و`SIGNED_IN` وAuth Callback وتسجيل الدخول عبر `completeAuthSession()` نفسه. هذه الدالة تضبط حالة `LOADING_DATA`، وتستأنف نية المطعم المعلّقة عبر `resume_pending_restaurant()`، وتجلب سياق المالك أو العضوية وحالة إدارة المنصة والقدرات، ثم تحسب الوجهة الوحيدة المناسبة. لا يُزال التحميل إلا بعد اكتمال هذه العملية. [1]

لا يُنتظر تنفيذ عمليات Supabase داخل callback الخاص بالمصادقة؛ بل تُرحّل إلى microtask، بما يتوافق مع قفل عميل المصادقة. كما تُلغى نتائج أي bootstrap أو طلب مطعم أو قدرات متأخر إذا تغيّرت الجلسة أو تم تسجيل الخروج. لا يوجد استعمال لـ`window.location.reload()`، ولا `return null` لإخفاء فشل المسار. [1]

في Onboarding، أصبح إنشاء المطعم وإنشاء قالب المنيو محميين بقفلين متزامنين باستخدام `useRef` إضافة إلى حالة الزر المرئية. قبل إدراج أقسام القالب، يفحص التطبيق إن كان الفرع الأساسي يحتوي على أقسام بالفعل؛ وفي تلك الحالة لا يعيد الإدراج، بل يُحدّث الجاهزية وينقل المستخدم إلى معاينة المنيو. [2]

## AUTH FLOW

| المرحلة | السلوك بعد الإصلاح | نتيجة التوجيه |
|---|---|---|
| تحميل التطبيق | تسجيل مستمع Auth ثم طلب الجلسة ثم bootstrap موحد إن وُجدت | تبقى واجهة التحميل حتى الجاهزية |
| لا توجد جلسة | تصفير سياق المالك والقدرات | `/login` أو استمرار الصفحة العامة |
| `INITIAL_SESSION` أو `SIGNED_IN` | استدعاء bootstrap واحد قابل لإعادة الاستخدام للجلسة نفسها | لا يوجد طلب استئناف متوازٍ لنفس الجلسة |
| session لمستخدم جديد بعد التأكيد | استئناف المطعم المعلّق ثم جلب المطعم | `/onboarding` عند غياب مطعم أو عند عدم اكتمال الإعداد |
| session لمالك مكتمل الإعداد | جلب السياق ثم تقرير الوجهة | `/dashboard` |
| session لموظف نشط | جلب العضوية والمطعم المرتبط | `/dashboard` |
| تسجيل الخروج أو تبدل المستخدم | إبطال الطلبات المعلّقة وتصفير المتجر | لا يمكن لاستجابة قديمة أن تعيد بيانات المستخدم السابق |

## EMAIL CONFIRMATION

يستمر `signUp()` و`resendVerificationEmail()` في إرسال رابط التأكيد إلى `/auth/callback` باستخدام `emailRedirectTo` من نفس origin. بعد التسجيل بلا Session، تبقى صفحة التسجيل مسؤولة عن نقل المستخدم إلى `/verify-email`، وهي صفحة واضحة تتضمن البريد المستهدف وإعادة الإرسال والعودة لتسجيل الدخول. [1]

تقبل صفحة callback روابط PKCE عبر `exchangeCodeForSession(code)` وروابط hash عبر Session المتاحة أو حدث Auth لاحق. بعد الحصول على Session لا تقرر الصفحة وجهتها مباشرة من افتراضات محلية؛ بل تنتظر النتيجة المركزية من `completeAuthSession()` ثم تستخدم الوجهة المعادة. الرابط غير الصالح أو المنتهي يعرض واجهة تعافٍ واضحة بدل شاشة فارغة. [3]

## RESTAURANT CREATION

إنشاء المطعم المقصود بعد تأكيد البريد لا يزال منوطًا بـ`resume_pending_restaurant()` الموجود في قاعدة البيانات ويعتمد على `auth.uid()`، وليس على owner ID مرسل من الواجهة. الاستدعاء idempotent بحسب عقد migration الحالي؛ ويجلب bootstrap المطعم بعد ذلك من قاعدة البيانات حتى تصبح حالة المتجر النهائية هي الحالة الفعلية. [1] [4]

مسار إنشاء المطعم الاحتياطي في Onboarding مخصص فقط للحساب الذي يصل بلا مطعم. قبل الإدراج، يفحص التطبيق المطعم الحالي للمالك. أما في حالة النقر السريع في الصفحة نفسها، فقفل `createRestaurantInFlight` يمنع تنفيذ طلب ثانٍ قبل انتهاء الطلب الأول. [2]

## MENU REDIRECT

قرار التوجيه لا يعتمد على Redirects موزعة بين Login وCallback وPublicRoute. الدالة `resolveUserDestination()` تُرجع `/onboarding` للمستخدم الذي لا يملك مطعمًا أو للمالك الذي لم يكمل Onboarding، وتعيد `/dashboard` للحساب المكتمل أو الموظف ذي العضوية النشطة. PublicRoute لا يوجه مستخدمًا authenticated إلى Dashboard بصورة عمياء، بل يستخدم القرار نفسه بعد اكتمال التحميل. [1] [5]

## WHITE SCREEN

عولجت مصادر الشاشة البيضاء المثبتة أو المحتملة بطبقات متكاملة. تبقى الحماية في التطبيق على حالة تحميل صريحة إلى أن يُحمّل سياق الجلسة، ويوجد في Onboarding حالة خطأ بديلة واضحة إذا فشل جلب بيانات المطعم أو الشبكة. هذه الحالة توفر إعادة محاولة حقيقية أو عودة إلى صفحة الدخول ولا تستخدم إعادة تحميل للنافذة. [1] [2]

أظهر الفحص البصري المحلي أن `/register` و`/verify-email` ورابط callback المنتهي وفتح `/onboarding` دون Session كلها تعرض واجهات صحيحة بلا شاشة بيضاء أو refresh أو loop ظاهر. [8]

## SECURITY

لم تُضف أي service role key أو تجاوز لـRLS أو بيانات ملكية يحددها العميل. يبقى RPC الخاص باستئناف المطعم هو نقطة الإنشاء بعد تأكيد البريد، ويعتمد على هوية الجلسة في Supabase. تُستخدم إجراءات الواجهة فقط لجلب المطعم المملوك أو عضوية الموظف النشطة؛ ولا يغيّر هذا العمل schema أو API routes أو إعدادات Supabase أو عقد البريد. [1] [4]

حراس منع التكرار في الواجهة يحسنون تجربة المستخدم ولا يُقدَّمون كبديل لقيود البيانات أو RLS. سلامة البيانات عبر الجلسات والأجهزة تبقى معتمدة على RPC وقيود قاعدة البيانات القائمة؛ وهذا متسق مع عدم تعديل مخطط قاعدة البيانات ضمن النطاق. [4]

## REMAINING ISSUES

لا توجد مشكلة برمجية مفتوحة مثبتة في الفحص الآلي أو البصري المحلي ضمن نطاق الإصلاح. لكن اعتماد إنتاجي نهائي للرحلة الكاملة لا يزال مشروطًا بتشغيل سيناريو حقيقي بحساب Owner/Test Account مصرح به؛ دون ذلك لا يمكن التصريح بأن Email Confirmation وOnboarding المحمي وكتابة `onboarding_completed` وevents التحليلات قد نجحت E2E في بيئة Production.

| البند المطلوب للتحقق النهائي | الحالة | المطلوب |
|---|---|---|
| رابط بريد حقيقي | غير متاح في الجلسة الحالية | توفير حساب اختبار وMailbox مصرح به أو فتح جلسة مالك مؤكد في المتصفح. |
| رحلة Onboarding غير مكتملة | غير متاح في الجلسة الحالية | فتح مطعم اختبار لا يزال `onboarding_completed=false`. |
| منع تكرار الإدراج في DB | غير متحقق E2E | النقر المتكرر وrefresh أثناء الحفظ ثم مراجعة صفوف المطعم/الأقسام/الأصناف. |
| Events في Production | غير متحقق E2E | إكمال الجاهزية والمشاركة ثم فحص `analytics_events` و`admin_owner_activation_funnel`. |

**CODE FIXES READY FOR REVIEW — E2E OWNER VERIFICATION REQUIRED BEFORE CLAIMING FULL PRODUCTION VERIFICATION.**
